# WP3 acceptance and handoff

Planning revision 1, 23 October 2026. Read with the [main plan](WP3_IMPLEMENTATION_PLAN.md), [work packages](WORK_PACKAGES.md) and [audit](../reports/wp3-audit-2026-10-23.md). Every test below is **proposed**, not a claim that a test exists or passes. Names are acceptance identifiers; place tests in the appropriate existing module or a focused new module, keeping files manageable.

## 1. Incoming state and test discipline

P00 requires the final WP2 checkpoint, its dirty-state manifest, changed interfaces and actual check results. The audit snapshot already contains C11's event-time extraction and shared reader construction. Do not reintroduce batch feature extraction, overwrite another agent's work or assume an old defect report describes the final code.

Tests use synthetic current items and bounded historical events, temporary databases, fake HTTP and explicit stub readers. They must not import root configuration that loads `.env`, read personal exports, download embeddings, call a provider, regenerate tracked fixtures or overwrite published results. Use the repository's isolated check runner after reviewing its final WP2 version. A key being present never authorizes network access. Use explicit fake/live modes and distinct accounting namespaces.

For a bug regression: arrange the actual hazardous state, demonstrate the old behavior is rejected or incorrect, then verify the repaired path. Avoid tests that merely assert helper names or inspect implementation strings. Preserve WP1's strict output, transaction and role-denial tests. Do not alter expected results to accommodate a new defect.

## 3. Verification ladder and evidence

1. **Baseline:** record final WP2 commit, uncommitted hashes, Python/tool versions, approved decisions and protected fixture/result hashes. Inventory only approved paths; never inspect `.env` to discover credentials. Review the isolated runner and its dependency availability before using it.
2. **Small offline regressions:** run targeted tests per package with fake transport and temp storage, including failure cases. Record exact command, exit code and relevant result count. Treat tests here as future work, not evidence already obtained by planning.
3. **Integration:** exercise tiny corrected synthetic replay, event-time feature differences, immutable draft persistence, concurrent accounting and role denial. Compare replay/adapter/exam semantics using fixed answers. Preserve no-peeking and manifest evidence from final WP2.
4. **Complete required checks:** run `make check` or the documented isolated Windows equivalent after the slice stabilizes, plus strict core/engine typing and new modules' lint/format checks. Missing tools/dependencies require the normal approval path; do not silently install them. Repeat broad checks only after relevant changes/failures.
5. **Installed artifact:** build/install offline with approved available tools, test resources outside checkout, and retain the wheel/version/hash and smoke command. Source-tree asset existence does not prove wheel inclusion.
6. **Later consumer acceptance:** WP5 real-exam cases, WP6 approved-action/draft consumption, WP7 quarantine workflow, WP9 browser editing and WP10 real B3 run their own end-to-end tests. WP3 hands off interfaces and component evidence; it cannot mark those results passed in advance.
7. **Optional live spike:** separate explicit provider/model/destination/cost authorization. Use synthetic input, strict bounded job and actual usage. Unknown support/pricing remains unverified until tested. No paid call is needed to complete the deterministic planning deliverable.

For each implementation slice retain: source/dirty hash; prompt/template/schema/model/feature versions; dataset/stub hashes and Clock cutoff; request and accounting namespace; test commands/results; safely aggregated request/attempt/cache/cost counts; failed/unknown results; protected-byte comparison; migration/rollback outcome; known remaining blockers. Do not publish prompt bodies, private maps, restored drafts or credentials as evidence.
